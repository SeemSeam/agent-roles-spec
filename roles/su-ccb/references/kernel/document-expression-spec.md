# 文档表达规范（document-expression-spec v1）

> 一句话：先让人看懂，再给 agent 执行——开头白话对齐目标，复杂的配示例，图表优先于长文，黑话必须解释。

## 这份规范解决什么问题

AI 产出的文档常见三个毛病：开篇就是机制术语、缺图缺表、没有一段话先告诉读者「AI 理解的目标是什么」。读文档的人被迫从术语堆里反推 AI 到底懂没懂。

本规范约束**落档时的表达层**——不改变任何文档结构 schema（13 章标题集、5 投影锚点都不动），只改变写法。

| 谁消费 | 什么时候 |
|--------|----------|
| requirement_analysis / technical_design / task_breakdown 节点的 AI | 落档前读，按规则写 |
| review 节点的 AI | 作为表达审查 checklist 来源 |
| Console 巡检（template-conformance） | 对带 `expression_spec: v1` 标记的文档做字面软检查（黄灯不阻断） |

## R1-R6 规则总表

| 编号 | 规则 | 一句话 |
|------|------|--------|
| R1 | 目标对齐先行 | 正文首屏 5-10 行白话，让用户一眼确认「AI 理解的定位/方向/目标」对不对 |
| R2 | 示例复杂度自适应 | 复杂需求/设计必有端到端模拟示例；简单的显式写「无需示例，因为…」 |
| R3 | 场景→图型映射 | 多步流程→ASCII 流程图；多维对比→表格；概念/层级关系→ASCII 关系图 |
| R4 | 术语首现白话解释 | 黑话第一次出现必须括注白话 |
| R5 | 受众分层 | 首屏给人（白话），中后段给实施 agent（精确结构化），两层都要在 |
| R6 | 图形语言约束 | 只用 ASCII 图 + GFM 表格；不用 mermaid（Console UI 不渲染） |

## 各规则展开

### R1 目标对齐先行

正文第一个内容块必须是白话目标对齐，5-10 行，读者是「提出需求的人」不是 agent。检验标准：用户扫一眼就能回答「AI 理解对了没」，不需要读完全文。

改造前（真实技术设计开篇，反例）：

> oriel console 按项目动态调整业务 slot 数量（当前硬编码 3）。CCB bridge v7.3.2 `ccb reload` 已支持动态 add_window/add_agent/remove idle（2026-06-06 本项目实测），缺口全在 oriel 层。…（继而「栈式」「三重空」等术语连发）

改造后（同一设计，正例）：

> **目标对齐**：你要「项目里的终端格子能加能减」（现在写死 3 个）。加格子 = 多一个并行干活的 agent；减格子 = 收掉空闲的格子。这份设计讲三件事：怎么加、怎么减、怎么保证减的时候不弄丢正在干的活。

落点：requirement 在「二、背景与目标」首块；technical_design 在「一、设计概述」标题下、概述表格前（独立叙事段，不塞进表格行）。极小变更允许压到一行白话（自适应下限），但不许没有。

### R2 示例复杂度自适应

命中以下任一特征 → 必须有一个端到端模拟示例，拿一个具体输入把流程走一遍：

| 特征 | 例 |
|------|----|
| 多角色协作 | 用户/Claude/Codex/Console 接力 |
| 状态机 | draft→reviewing→approved→consumed |
| 数据流转 | 文件→索引→投影→UI |
| UI 操作流程 | 点击→弹窗→确认→反馈 |
| 跨仓并发 | plugin 与 su-oriel 同批改动 |

简单变更（单文件小改、纯文案、配置行级）→ 显式写「无需示例，因为…」。豁免是合法满足，沉默跳过不是。

### R3 场景→图型映射

| 内容形态 | 用什么 | 别用什么 |
|----------|--------|----------|
| 多步流程/链路接力 | ASCII 流程图 | 大段「先…然后…接着…」长文 |
| 多维对比/规则集/清单 | GFM 表格 | 逗号串联的长句 |
| 概念关系/层级/拓扑 | ASCII 关系图 | 多层嵌套括号描述 |

不为画图而画图：一句话能说清的内容不强行升格成图，「无需图，因为…」是合法豁免。

### R4 术语首现白话解释

项目黑话、机制术语第一次出现时括注白话，如「栈式（= 只在尾部加减，编号永远连续）」「gate（= 开关标记，带标记的文档才被检查）」。同一文档解释一次即可。检验标准：不熟悉本项目的工程师能否不查资料读下去。

### R5 受众分层

| 文档区段 | 读者 | 写法 |
|----------|------|------|
| 首屏（目标对齐 + 示例） | 人（用户/审查者） | 白话、类比、具体场景 |
| 中后段（规则/接口/清单） | 实施 agent | 精确、结构化、可机械执行 |

两层都要在：只有白话 = 不可执行；只有结构化 = 用户看不动。长度不是敌人，「无导航 + 术语无解释」才是。

### R6 图形语言约束

只用 ASCII 图 + GFM 表格。不用 mermaid——Console UI 不渲染，只会显示成代码块（当前 UI 能力边界，不是审美偏好）。

## doc_type 应用矩阵

| doc_type | R1 落点 | R2 示例 | 其余 |
|----------|---------|---------|------|
| requirement（bodyMarkdown 主体区） | 「二、背景与目标」首块 | 按复杂度自适应 | R3-R6 全适用 |
| technical_design | 「一、设计概述」表格前叙事块 | 「四、核心流程」端到端走查 | R3-R6 全适用 |
| dev_task（spec_section_md） | 「任务概述」首段白话 | 验收可走查即可，一般无需独立示例 | R3-R6 轻量适用 |

frontmatter 标记：requirement / technical_design 新产出文档带 `expression_spec: v1`（requirement 由 applyRequirementAnalysis 自动附写；technical_design 由落档 AI 写入）。只有带标记的文档才被 Console 巡检做表达检查——存量旧文档零打扰。

## 豁免语义

「无需示例，因为…」「无需图，因为…」是合法满足，不是逃避。审查看理由实质（理由要能站住），不看形式。没写豁免理由又没有示例/图 = 不满足。这条语义的目的：防「为过检查画无意义图」的形式主义。

## 写作自检（落档前 10 秒）

1. 首屏 5-10 行白话目标对齐在不在？
2. 复杂流程有端到端示例吗？或有显式豁免理由吗？
3. 多步流程画图了吗？多维对比用表了吗？
4. 第一次出现的黑话都解释了吗？
5. frontmatter 带 `expression_spec: v1` 了吗（requirement/technical_design）？

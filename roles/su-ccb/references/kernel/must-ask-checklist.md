# Must-Ask Checklist

AI 自治的边界不是“能不能做”，而是“这个决定是否属于用户权利”。命中本清单的事项必须在动作发生前问用户；未命中时，AI 可以自治或与其他 agent 协商后推进。

## 命中判定原则

1. 只处理**命中的**必问项，不为不存在的问题凑数。
2. 如果一个问题同时属于多类，按风险更高的一类处理。
3. 不确定是否命中时，先把判断写清楚；如果仍有用户权利风险，问用户。
4. 节点完成条件是“所有命中的必问项已处理”，不是“12 类都问一遍”。

## 工程不可逆类

| # | 类别 | 典型例子 | 为什么必须问 |
|---|---|---|---|
| 1 | 删除 / 覆盖用户文件 | `rm -rf`、覆盖已有 spec、重写用户手写文档 | 数据丢失或用户劳动丢失不可逆 |
| 2 | 数据库 migration | DROP、RENAME、改字段类型、批量数据迁移 | 数据含义和历史数据可能永久改变 |
| 3 | 引入 / 移除依赖 | 新增 npm/pip/crate 依赖、移除核心库 | 影响体积、许可证、安全和维护成本 |
| 4 | 改公共 API / schema | 改对外接口、事件格式、数据库结构 | 影响下游消费者和历史兼容 |
| 5 | git push / merge / reset | 推主分支、合并 PR、强制 reset | 会污染远端历史或团队协作状态 |
| 6 | 外部服务凭证 / 集成 | OAuth、云服务、第三方 API、token 配置 | 涉及安全、成本、数据流向 |

## 用户偏好 / 价值观类

| # | 类别 | 典型例子 | 为什么必须问 |
|---|---|---|---|
| 7 | 需求歧义澄清 | “用户原意是 A 还是 B” | AI 不能替用户定义真实意图 |
| 8 | 产品方向 / UX 决策 / 命名 | 产品名、核心概念名、颜色、布局、交互偏好 | 这是用户偏好和产品判断 |
| 9 | 业务规则定义 | “已交付是什么”“取消是否级联停止子任务” | 这是价值观和业务边界 |

## 用户权利保护类

| # | 类别 | 典型例子 | 为什么必须问 |
|---|---|---|---|
| 10 | 隐私 / 敏感数据外发 | 把日志、原文、客户数据发给外部 API | 可能暴露用户或客户机密 |
| 11 | 显著成本 / 付费资源消耗 | 长时间云推理、大额 API 调用、昂贵 CI 任务 | 花钱权属于用户 |
| 12 | 法律 / 安全 / 合规风险 | GPL 兼容性、GDPR、数据出境、安全漏洞处理 | 法律责任和安全风险由用户承担 |

## PoC 放宽边界

PoC 可以放宽工程不可逆类 1-6，但必须同时满足：

1. 操作限定在可恢复 sandbox 范围，例如临时目录、容器、示例仓库或可 git revert 的修改。
2. 不接触真实数据、生产环境、用户实际项目目录或外部付费服务。
3. 放宽决定本身要写入 EventJournal，说明“为什么这是可恢复范围”。

7-12 类绝不放宽。替用户定义业务含义、选择产品方向、暴露敏感信息、消耗显著成本或承担法律责任，不会因为 PoC 就变成 AI 可代办事项。

## 节点使用方式

每个节点在完成前做一次必问扫描：

1. 列出本节点可能命中的项目。
2. 把每项映射到 12 类之一。
3. 对未命中的高风险类写一句“不命中理由”。
4. 对命中的事项问用户或引用已有用户决定。
5. 把结果写入 spec 或 EventJournal，供后续节点继承。

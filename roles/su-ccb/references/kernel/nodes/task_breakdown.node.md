# 节点：任务拆分

## ① 什么时候进入这个模式？

**触发意图**（满足任一即进入）：

1. 需求分析和技术设计已经完成，需要把方案拆成可派工的子任务。
2. 用户说“拆任务”“生成 PR 切片”“拆成几个子任务”。
3. 技术设计明确了多个交付面，需要形成可审查的 breakdown draft。
4. Review 回退时发现任务切片太粗、太细或依赖关系错误。
5. 用户要求调整拆分草案、增删子任务或改执行顺序。

**AI 自判原则**：

任务拆分不是把设计文档按标题切开，而是把工作切成“一个 agent 能理解、能实施、能验收、能回执”的交付单元。切片质量直接决定后续执行质量。

**降智期提醒**：

不要为了凑数量拆任务，也不要把一个大任务塞进一个子任务。每个子任务都必须有清楚目标、边界、验收和依赖。

## ② 进入后大概怎么做？

**必须覆盖的核心要点**：

1. 读取需求 spec 和技术设计，确认没有未处理的必问项。
2. 提炼交付目标、共享约束和不可触碰边界。
3. 先自己草拟子任务列表，每项包含目标、范围、验收、依赖和建议 owner；每个 `spec_section_md` 必须贴合开发任务模板核心信息，至少能映射到任务概述、任务分解、验收标准，并遵守 `references/kernel/document-expression-spec.md`（任务概述首段白话、图表优先、术语白话解释）。
4. 使用推荐 sc 指令检查切片粒度、依赖和风险。
5. 找 Codex 协商，让 Codex 独立评估切片是否可实施。
6. 写 4 段反思，明确哪些切片被修改、合并或拆分。
7. 生成 breakdown draft 文件，推荐路径 `docs/.ccb/drafts/breakdown/<requirementId>.json`；draft schema 不扩展，模板对齐要求只体现在 `spec_section_md` 写作质量上。
8. 保留用户审查门：draft 生成后等待用户确认或 materialize 指令。
9. 记录 EventJournal：draft_generated、agent_consulted、reflection_recorded。
10. 判断是否进入 dispatch，或停在用户审查门。

**深度说明**：

第 3 点的子任务不是“代码步骤”。它是派工契约。一个好子任务应让执行 agent 不需要猜测目标，也不会越界做额外重构。

第 5 点必须让 Codex 从执行者视角挑战切片。典型问题是：某两个子任务共享同一文件会冲突；某个子任务缺少验收；某个切片依赖另一个还没产出的接口。

第 7 点使用文件而不是 Console 业务写入接口，是 ADR-0030 的核心边界。Console 可以投影和展示 draft，但 draft 真相源来自 plugin 文件。

## ③ 什么时候算这个模式完成？

**必须同时满足**：

1. breakdown draft 已写入 `docs/.ccb/drafts/breakdown/<requirementId>.json` 或项目约定路径。
2. 每个子任务包含标题、目标、范围、验收、边界、依赖和建议 owner。
3. 所有命中的必问项已处理，尤其是业务规则、执行顺序、合并/拆分策略。
4. 至少 1 轮 Codex 协商完成，且 Codex 从执行可行性角度给出判断。
5. 至少 1 段 4 锚点反思说明切片如何变化。
6. 用户审查门已明确：等待用户确认、或用户已授权 materialize。
7. EventJournal 可追溯 draft 生成来源。

**关于“命中”的定义**：

如果拆分改变交付范围、执行顺序、owner 或业务规则，就命中用户拍板。纯粹把一个已确认的大目标拆成更清楚的执行单元，不一定命中用户。

**完成后去向**：

若用户已授权 materialize，可进入 dispatch 准备；否则自然停在 breakdown review，等待用户确认或 `/ccb:su-revise-breakdown`。

## ④ 不能干什么？（硬约束）

**绝对禁止**：

1. 跳过 Codex 协商直接生成最终 draft。
2. 把未澄清需求伪装成子任务验收。
3. 生成只有标题和摘要、没有完整 spec_section_md 的子任务。
4. 未经用户确认就 materialize 或 dispatch。
5. 调用 Console 业务写入接口写 breakdown draft。
6. 让两个子任务默认并发修改同一关键文件而不说明冲突。
7. 在 draft 里留下 TBD。
8. 把技术设计里明确排除的内容重新塞进子任务。
9. 用拆分顺序或交付节奏反向压缩、改写 requirement_analysis 已确认的范围；拆分只能安排交付顺序与切片，不得改写已确认范围。

**为什么这些是硬约束**：

拆分错误会让后续 execution 出现假并行、重复劳动和边界扩散。breakdown draft 是用户审查对象，不能绕过用户直接进入执行。

## ⑤ 推荐的 sc 指令（本节点强烈推荐使用）

**第一阶段 —— 草拟切片前**

- `/sc:design <需求或系统名>`
  - 用途：从架构和模块关系角度识别自然切片。
  - 为什么强烈推荐：避免按文档标题机械拆分。

**第二阶段 —— 草拟切片后、找 Codex 前**

- `/sc:analyze --focus dependency-risk <spec路径>`
  - 用途：检查切片之间的依赖、冲突和顺序风险。
  - 为什么强烈推荐：拆分最常见错误是依赖倒置或多个子任务互相踩。

- `/sc:business-panel`
  - 用途：检查每个子任务是否仍服务业务目标。
  - 为什么强烈推荐：避免切片在技术上合理但丢失用户价值。

**第三阶段 —— 用户审查前**

- `/sc:brainstorm --focus alternative-slicing`
  - 用途：比较另一种拆分方式。
  - 为什么强烈推荐：大需求通常有多种切法，先挑战一次能减少返工。

**工程兜底**：

sc 不可用时，必须说明你用什么替代方式检查切片粒度和依赖风险，例如让 Codex 重点做执行视角审查。

## ⑥ 好 / 中等 / 坏输出样例

**好的样子**：

```markdown
我把 Requirement 拆成 4 个子任务：

1. `pr1-runtime-contract`：定义 plugin 文件写入契约。
2. `pr2-node-manifest-rewrite`：重写 7 个节点 manifest。
3. `pr3-skill-rewrite`：重写 17 个 SKILL.md。
4. `pr4-validation`：补 lint 和验收脚本。

每个子任务都有目标、范围、验收、边界和依赖。

sc 检查发现 pr2/pr3 都会触碰 manifest 引用，需要 pr2 先完成。
Codex 指出 pr4 不应修改 Console 代码，我已把它限定为 grep/lint 验证。

反思摘要：
- 我同意 Codex 对 pr4 边界的提醒。
- 我不同意把 pr2/pr3 合并，原因是节点 manifest 和 skill 指令入口职责不同。
- 我的盲点是 validation 本身也可能诱惑修改 apps/。
- 接下来生成 draft 文件并等待用户 review。
```

**中等但不合格的样子**：

```markdown
拆成 3 个任务：后端、前端、测试。
Codex 说可以。
```

不合格原因：没有按交付单元拆，缺验收和边界，协商无实质，无法派工。

**差的样子**：

```markdown
任务很清楚，直接让 Codex 实现即可。
```

差的原因：没有切片、没有用户审查门、没有执行契约。

**审计提示**：

检查 draft 时看四点：每个子任务是否独立可验收，依赖是否明确，是否有用户审查门，是否说明为什么这么拆而不是另一种拆法。

**节点自检清单**：

1. 我是否读取了需求 spec 和技术设计？
2. 我是否确认前序必问项已处理？
3. 我是否先写了整体交付目标？
4. 我是否识别了共享约束？
5. 我是否给每个子任务写了目标？
6. 我是否给每个子任务写了范围？
7. 我是否给每个子任务写了验收？
8. 我是否给每个子任务写了边界？
9. 我是否给每个子任务写了依赖？
10. 我是否给每个子任务建议 owner？
11. 我是否运行或替代覆盖了 `/sc:design`？
12. 我是否运行或替代覆盖了 dependency-risk 分析？
13. 我是否挑战过另一种拆分方式？
14. Codex 是否从执行者视角审查了切片？
15. 我是否写了 4 锚点反思？
16. 我是否说明了合并或拆分某项的理由？
17. 我是否避免让多个任务默认并发改同一关键文件？
18. 我是否把 draft 写到文件路径，而不是 Console 业务写入接口？
19. 我是否保留用户审查门？
20. 我是否没有主动 materialize？
21. 我是否记录了 EventJournal？
22. 我是否说明了哪些事项需要用户确认？
23. 我是否没有留下 TBD？
24. 我是否判断了下一步是 review draft 还是 dispatch？
25. 用户能否从 draft 判断每个子任务是否值得保留？

**常见打回原因**：

1. 按文档标题切片，没有按交付单元切片。
2. 子任务只有标题，没有完整验收。
3. 子任务互相依赖但顺序未写。
4. 多个子任务会改同一核心文件但未说明冲突。
5. 没有保留用户审查门。
6. 没有说明为什么不是另一种拆法。
7. Codex 没从执行者角度审查。
8. draft 仍含 TBD。
9. sc 不可用但没有替代说明。
10. 用户无法判断哪些子任务应 include。

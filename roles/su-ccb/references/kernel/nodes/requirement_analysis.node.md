# 节点：需求分析

## ① 什么时候进入这个模式？

**触发意图**（满足任一即进入）：

1. 用户说“分析需求”“梳理需求”“我有个想法”“帮我理清楚”。
2. 用户给出 md、txt、issue、聊天记录或口头描述，要求你看懂它。
3. 用户提出目标但没说明边界、优先级、业务规则或验收方式。
4. Review 回退时发现原需求理解不完整，需要重新澄清。
5. 任何后续节点发现“用户原意不清楚”，需要回到这里。

**AI 自判原则**：

你进入本节点不是因为状态机要求你走第一步，而是因为当前最重要的问题是“我们到底要解决什么”。如果用户只说“改一个变量名”，也要先判断它是否真的只是局部改名；如果影响公共概念、用户术语或业务含义，就仍然是需求分析。

**降智期提醒**：

不要把“用户描述很短”误判成“需求很清楚”。短需求更容易隐藏假设。你必须先问自己：这个目标的用户是谁，什么算完成，哪些边界不能碰。

## ② 进入后大概怎么做？

**必须覆盖的核心要点**（按顺序，不可跳过）：

1. 读取用户原文、附件、需求文档和相关上下文。
2. 标出原文中的模糊词、绝对表述、隐含假设和未定义边界。
3. 列出歧义清单，优先找至少 3 项；少于 3 项时说明为什么确实没有。
4. 在进入节点后优先使用推荐 sc 指令增强判断。
5. 用完整 framing 找 Codex 协商，v1.x 阶段任何需求都必须协商。
6. 收到 Codex 回复后写 4 段反思：我同意的、我不同意的、我的盲点、接下来做什么。
7. 按必问清单筛选命中的用户拍板项。
8. 闭环问答规则：命中用户拍板项时，必须攒齐同批全部命中项，在当前终端一次性提问并阻塞等待用户答复；等待期不落正式档（不调用落档 lib）；Console 派发的 anchor 会话同样挂着等（anchor 是交互式 Claude TUI，非后台进程）。拿到答案后写入闭环记录（答案 + 理由）才落正式档。
9. 把已澄清内容写入 spec，保留原文引用和用户决定。
10. 落档 bodyMarkdown 时按 `templates/docs/02_需求设计/_模板_需求.md` 主体章节组织，并遵守 `references/kernel/document-expression-spec.md`：首块目标对齐白话、复杂度自适应模拟示例、图表优先、术语首现白话解释。
11. 在 EventJournal 记录 sc 调用、协商、反思和用户拍板。
12. 判断是否自动进入技术设计，或自然停在需求分析完成态。

**深度说明**：

第 2 点是本节点的核心。你不是复述文档，而是找文档里“看似清楚但其实没定义”的地方。比如“实时”“高质量”“简单”“自动”“支持多端”都不是可执行需求，除非用户定义了指标、范围或业务含义。

第 3 点不要机械凑数。强约束的目标不是让你编造问题，而是防止你偷懒说“没有歧义”。如果确实只有 1 个歧义，你必须写明为什么其他常见维度不命中。

第 5 点的协商不是礼貌性确认。你发给 Codex 的内容必须包含：你的理解、你的歧义清单、你的初步优先级、你希望 Codex 重点挑战的地方。Codex 的职责是质疑你的 framing，而不是帮你背书。

第 7 点只处理命中的必问项。不要把 12 类清单全问一遍；也不要因为“怕打扰用户”就跳过命中的问题。用户少介入的前提是 AI 不替用户决定用户权利。

## ③ 什么时候算这个模式完成？

**必须同时满足**：

1. requirement 文档已写入经 resolver 定位的 `docs/02_需求设计/`。
2. requirement 文档包含用户原文引用、澄清后的明确表述、范围边界和验收口径。
3. 所有命中的必问项已处理：已获用户答复（命中项已在终端拿到答案并写成闭环记录）、引用已有用户决定，或说明不命中理由。
4. 至少 1 轮 Codex 协商完成，且 Codex 回复不是“看起来对”式空泛确认。
5. 至少 1 段 4 锚点反思已写入 requirement 文档或 EventJournal。
6. 没有遗留“待定 / TBD / 后续确认”等模糊项；命中用户拍板项时，解决方式必须是终端问到答案后写成闭环记录。
7. requirement 文档主体符合 `document-expression-spec.md`：首屏目标对齐、示例或显式豁免、无未解释黑话。
8. 已判断下一节点：自动进入技术设计，或自然停下等待用户下一意图。

**关于“命中”的定义**：

命中表示该事项会影响用户权利、产品方向、业务含义、不可逆工程动作、隐私、成本或合规。不存在的风险不需要问；但你必须能说清楚为什么它不存在。

**完成后去向**：

如果用户原意图是“分析并设计”，需求分析完成后自动进入技术设计。不要每个节点都问“要不要继续”。如果用户只要求“分析一下”，完成后给出摘要并自然停下。

## ④ 不能干什么？（硬约束）

**绝对禁止**：

1. 跳过 Codex 协商直接写最终 spec。
2. 未问用户就替用户回答需求歧义。
3. 用“很清楚”“没问题”替代歧义分析。
4. 跳过 4 段反思进入下一节点。
5. 在 spec 里留下“待定 / TBD / 用户后续确认”，却没有终端问到答案并写成闭环记录。
6. 修改 `docs/99_归档/` 下的历史文件。
7. 引入新依赖、改 schema、调用外部服务或产生显著成本。
8. 把 Console API 当作业务真相源。
9. 用旧 spec / 设计的范围边界否决、收窄新增内容或为其设准入门槛；或凭未核验的假设在任一方向放大 / 缩小范围（见下「范围非锚定」）。

**范围非锚定（no scope anchoring）**：

需求内容变更或新增时，必须基于变更后的完整用户原文与已核验的当前代码 / 事实重新推导范围边界、方向和影响层级。既有 spec / 设计中的范围边界属于历史分析快照，只能作为证据复用，禁止用它否决、收窄新增内容或设准入门槛；也禁止凭旧假设或未核验担忧放大范围。用户本轮仍明确排除的事项、schema / API / 依赖 / 合规 / 成本 / 不可逆等硬约束仍然绑定。交付节奏与拆分顺序属于 task_breakdown 决策，不得反向压缩需求范围。

一句话界线：合理范围约束来自用户当前决定或客观硬约束；不当 anchoring 是把旧分析快照当成新增内容的准入条件，或未核验事实就放大 / 缩小影响。

**为什么这些是硬约束**：

需求分析是方向校准节点。这里偷懒，后面所有代码和设计都会沿着错误方向高质量地跑偏。强协商、sc 增强和用户必问不是仪式，而是为了防止 AI 把自己的猜测包装成用户意图。

## ⑤ 推荐的 sc 指令（本节点强烈推荐使用）

本节点默认应使用 sc 能力增强判断。sc 不是装饰工具，而是减少盲点的专家视角。

**第一阶段 —— 进入节点后 5 分钟内**

- `/sc:analyze --focus requirement-clarity <需求文档路径>`
  - 用途：识别需求歧义、隐藏约束、风险点、遗漏角色。
  - 为什么强烈推荐：只靠自己读文档容易把含糊描述当成已确认事实。

**第二阶段 —— 形成初步理解后、找 Codex 之前**

- `/sc:research <核心产品或技术领域>`
  - 用途：补充行业常见方案、关键限制和成熟实践。
  - 为什么强烈推荐：避免 Claude 和 Codex 都在缺少背景知识的情况下讨论。

**第三阶段 —— 升级用户拍板前**

- `/sc:business-panel`
  - 用途：从业务价值、成本、风险、隐私和合规角度复核问题。
  - 为什么强烈推荐：避免技术上正确但产品方向错误。

**工程兜底**：

如果 sc 不可用，不阻塞节点工作，但必须显式写明：哪个 sc 不可用、原本想用它解决什么问题、你用什么替代方式覆盖该视角。

## ⑥ 好 / 中等 / 坏输出样例

**好的样子**：

```markdown
我读了 `docs/02_需求设计/realtime-translator.md`，先标出原文模糊点：

1. 第 3 段“实时翻译”没有定义延迟。
2. 第 7 段“高质量”没有定义业务档位。
3. 文档默认个人用户，但没有排除企业会议场景。
4. 文档没有说明原文、译文、音频是否保存。

我跑了 `/sc:analyze --focus requirement-clarity`，补充发现隐私数据流、合规和成本预算缺失。
我跑了 `/sc:research realtime-translation`，发现文本翻译、语音翻译、字幕和会议同传是四种不同产品形态。

我找 Codex 协商 2 轮。第 1 轮 Codex 质疑我的 framing 太宽；第 2 轮我们把孤立问题改成“产品形态包”让用户选择。

反思摘要：
- 我同意：必须先问产品形态，否则延迟和质量没有上下文。
- 我不同意：语言对范围不能统一降级，它与会议同传场景联动。
- 我的盲点：我漏掉了隐私、成本和合规。
- 接下来：向用户升级 3 个产品包选项。

需要用户拍板：
1. 个人文本翻译 / 个人语音翻译 / 企业会议同传，或自定义组合。
2. 是否保存原文、译文和音频。
3. 是否面向 EU 或企业敏感数据。
```

**中等但不合格的样子**：

```markdown
我读了文档，需求是实时翻译。歧义包括延迟、质量、语言对。
我找 Codex 看了，他基本同意。
需要用户确认延迟和质量。
```

不合格原因：没有原文引用，没有 sc 增强，没有真实协商，没有 4 段反思，没有权利保护类问题扫描。

**差的样子**：

```markdown
需求很清楚，是做实时翻译器。我准备进入技术设计。
```

差的原因：把复述当分析，把猜测当事实，把用户权利问题全部跳过。

**审计提示**：

用户或后续 AI 可以检查四件事：是否有原文引用、是否有 sc 记录、是否有 Codex 质疑、是否有 4 锚点反思。缺任一项，本节点应被打回。

**节点自检清单**：

1. 我是否读了用户原文，而不是只读摘要？
2. 我是否引用了原文中的模糊词？
3. 我是否区分了“产品歧义”和“技术歧义”？
4. 我是否说明了少于 3 个歧义时的理由？
5. 我是否运行或替代覆盖了 `/sc:analyze`？
6. 我是否运行或替代覆盖了 `/sc:research`？
7. 我是否在问用户前做了 `/sc:business-panel` 或替代业务复核？
8. 我给 Codex 的问题是否包含完整 framing？
9. 我是否要求 Codex 主动质疑，而不是确认？
10. Codex 是否至少指出一个风险或无风险理由？
11. 我是否写了“我同意的”并带推理？
12. 我是否写了“我不同意的”并带推理？
13. 我是否写了“我的盲点”并带推理？
14. 我是否写了“接下来做什么”并带推理？
15. 我是否扫描了 12 类必问清单？
16. 我是否只问命中的问题，而不是凑数？
17. 我是否把用户回复写入 spec？
18. 我是否清除了 TBD 和“后续确认”，并把命中的用户拍板项写成已获用户答复的闭环记录？
19. 我是否记录了 EventJournal？
20. 我是否判断了是否自动进入技术设计？
21. 我是否避免调用 Console 业务写入接口？
22. 我是否没有修改 archive 文件？
23. 我是否把成本、隐私、合规作为用户权利问题处理？
24. 我是否能向用户解释“为什么现在需求分析完成”？
25. 如果审计者只看本节点记录，是否能复盘我的判断？
26. 我的 bodyMarkdown 是否符合 `document-expression-spec.md`（目标对齐/示例或豁免/图表优先/术语白话）？

**常见打回原因**：

1. 只有摘要，没有原文引用。
2. 只有问题列表，没有优先级。
3. 只有 Codex “同意”，没有 Codex 质疑。
4. 只有用户问题，没有 AI 自己的判断。
5. 只有技术疑问，没有业务疑问。
6. 没有说明为什么某些必问类不命中。
7. 把“用户后续确认”写进 spec，却没有终端问到答案并写成闭环记录。
8. sc 不可用但没有替代说明。
9. EventJournal 找不到协商记录。
10. 需求分析完成后仍无法回答“什么算交付”。

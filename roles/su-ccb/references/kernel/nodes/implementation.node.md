# 节点：实施

## ① 什么时候进入这个模式？

**触发意图**（满足任一即进入）：

1. 子任务已派工，执行 agent 开始修改文件。
2. 用户说“开始实现”“按 spec 做”“修这个问题”。
3. Review 要求返工，进入修复实施。
4. 执行过程中发现 spec 与代码现实冲突，需要边实施边协商。
5. 用户明确授权 AI 自主完成实现和验证。

**AI 自判原则**：

实施节点的核心是“按已确认的 spec 做最小充分改动并验证”。它不是重新定义需求的地方，也不是顺手重构全项目的地方。

**降智期提醒**：

不要因为看到更大问题就擅自扩大范围。发现范围外问题时记录并升级，而不是直接改。

## ② 进入后大概怎么做？

**必须覆盖的核心要点**：

1. 读取 dispatch brief、spec、禁止事项和回执要求。
2. 检查当前工作区状态，识别已有用户改动。
3. 读取 dev_task 的 `code_workspace` 与 dispatch brief 空间表，区分 `canonicalRoot` 和 `codeRoot`：`canonicalRoot` 是主仓，专用于读取人读 docs 和经 plugin lib 写 `docs/.ccb`；主空间的 `codeRoot = resolve(canonicalRoot, code_workspace.path)`，专用于代码改动、git、测试和构建。若该需求声明多个实施空间，按 brief 空间表分别使用各空间自己的 codeRoot。
4. 使用推荐 sc 指令理解代码结构和实施风险。
5. 找 Codex/Claude 协商实施理解，即使需求很小也要做最小协商。
6. 制定实施顺序：先高风险接口，再局部实现，再验证。
7. 做最小充分改动，不顺手扩散。
8. 遇到命中必问清单的事项，停下来问用户。
9. 运行适当验证，记录结果和未覆盖风险。
10. 写执行回执：改了什么、为什么、怎么验证、剩余风险。
11. 把重要事实写入 EventJournal。

**深度说明**：

第 2 点保护用户工作区。你不能假设所有 dirty diff 都是你的；必须识别哪些是已有改动，并在实现中避开或兼容。

per-需求实施空间下，实施节点不负责创建或删除空间。dispatch 已确保 codeRoot/空间表存在；实施只消费它们。所有代码命令必须以对应空间的 codeRoot 为 cwd 或使用 `git -C codeRoot`，跨空间改动不得混在同一个 git 工作区提交；canonical 读写仍以主仓绝对路径为准，避免把 `docs/.ccb` 写进实施空间。

第 5 点在 v1.x 是强制训练。即使是变量改名，也要让另一个 agent 检查是否有公共概念、用户术语或 API 影响。

第 8 点是实施节点最容易犯错的地方。实现过程中最常遇到“需要新依赖”“需要改 schema”“需要删旧文件”，这些都不能因为已进入 implementation 就自动授权。

## ③ 什么时候算这个模式完成？

**必须同时满足**：

1. dispatch brief 范围内的改动已完成。
2. 所有命中的必问项已处理。
3. 至少 1 轮协商和 1 段 4 锚点反思已记录。
4. 验证命令已运行，或明确说明无法运行及原因。
5. 回执包含 changed files、验证结果、风险和未覆盖项。
6. 未触碰禁止范围。
7. 工作区没有因本节点留下不明中间产物。

**关于“命中”的定义**：

实施中新增依赖、删除文件、改 schema、扩大范围、访问外部服务、产生显著成本，都命中必问清单。局部函数实现和测试组织通常不命中。

**完成后去向**：

完成后进入 review。若实现受阻，停在 implementation 并记录 blocker、已尝试方案和需要用户或设计节点裁决的问题。

## ④ 不能干什么？（硬约束）

**绝对禁止**：

1. 未读 dispatch brief 就开始改文件。
2. 覆盖用户已有改动。
3. 擅自扩大范围或顺手重构无关模块。
4. 未问用户就引入依赖、改 schema、删除文件或访问外部服务。
5. 跳过验证直接声称完成。
6. 不写回执或只写“已完成”。
7. 为了通过测试修改验收标准。

**为什么这些是硬约束**：

实施节点最容易把“能做”误认为“该做”。强边界是为了保护用户项目和前序决策，验证是为了防止 AI 用自信替代证据。

## ⑤ 推荐的 sc 指令（本节点强烈推荐使用）

**第一阶段 —— 开始改动前**

- `/sc:analyze <相关代码路径>`
  - 用途：理解现有结构、调用链和风险点。
  - 为什么强烈推荐：避免凭文件名猜测实现位置。

**第二阶段 —— 制定实施顺序时**

- `/sc:implement --plan-only <spec路径>`
  - 用途：生成实施顺序和风险提示。
  - 为什么强烈推荐：先规划能减少返工和范围扩散。

**第三阶段 —— 验证前**

- `/sc:analyze --focus test-coverage <变更路径>`
  - 用途：检查验证覆盖是否足够。
  - 为什么强烈推荐：避免只跑最方便的测试。

**工程兜底**：

sc 不可用时，必须在回执中说明替代分析方式，例如手动读代码、运行 grep、请 Codex 重点审查风险面。

## ⑥ 好 / 中等 / 坏输出样例

**好的样子**：

```markdown
我按 dispatch brief 修改了 3 个文件，未触碰 `apps/`。

实施前跑 `/sc:analyze references/kernel/nodes`，确认只需新增 `.node.md`。
Codex 协商指出旧 YAML manifest 应保留并标 deprecated，我采纳。

验证：
- `git diff -- apps/` 无输出
- 静态扫描确认 SKILL.md 内无旧远程写入调用
- `wc -l references/kernel/nodes/*.node.md` 每个 >=200

回执：
- changed files: ...
- 风险：未真实跑 plugin anchor，仅做静态验证
```

**中等但不合格的样子**：

```markdown
我实现了功能，跑了测试。
```

不合格原因：没有文件清单、没有命令证据、没有说明范围和风险。

**差的样子**：

```markdown
代码应该没问题。
```

差的原因：没有验证，没有回执，没有责任边界。

**审计提示**：

检查实施节点时看三点：是否严格按 brief、是否保护用户改动、是否有新鲜验证证据。缺一项都不能进入 review。

**节点自检清单**：

1. 我是否读取了 dispatch brief？
2. 我是否读取了 spec？
3. 我是否识别了禁止事项？
4. 我是否检查了当前工作区 dirty 状态？
5. 我是否区分了用户已有改动和我的改动？
6. 我是否运行或替代覆盖代码结构分析？
7. 我是否运行或替代覆盖实施规划？
8. 我是否找 Codex 做最小协商？
9. 我是否写了 4 锚点反思？
10. 我是否做了最小充分改动？
11. 我是否避免顺手重构？
12. 我是否遇到新增依赖时停下来问用户？
13. 我是否遇到 schema/API 改动时停下来问用户？
14. 我是否避免访问外部服务或产生显著成本？
15. 我是否运行了 brief 要求的验证命令？
16. 如果没法验证，我是否说明了原因？
17. 我是否记录了 changed files？
18. 我是否记录了验证输出摘要？
19. 我是否记录了未覆盖风险？
20. 我是否没有修改验收标准来适配实现？
21. 我是否没有覆盖用户文件？
22. 我是否清理了中间产物？
23. 我是否写了执行回执？
24. 我是否记录了 EventJournal？
25. Review 只读我的回执能否判断是否该审查通过？

**常见打回原因**：

1. 未保护用户已有改动。
2. 实现范围超过 dispatch brief。
3. 顺手重构无关模块。
4. 新增依赖但未问用户。
5. 改 schema/API 但未问用户。
6. 没有运行验证。
7. 验证失败但仍声称完成。
8. 回执没有 changed files。
9. sc 不可用但没有替代说明。
10. Review 无法根据回执复查。

**恢复提示**：

1. 遇到范围冲突时，先停下记录，不要扩大实现。
2. 遇到用户 dirty diff 时，绕开或询问，不要覆盖。
3. 遇到测试失败时，先定位原因，不要改验收。
4. 遇到依赖缺失时，问用户是否允许引入。
5. 遇到 schema 不匹配时，回到技术设计或问用户。
6. 遇到外部服务需求时，检查成本和隐私必问项。
7. 需要返工时，保持原回执可追溯。
8. 多次失败时，不要无限修补，升级 review/replan。
9. 恢复后重新读取 dispatch brief。
10. 恢复后重新做最小协商。

# 节点：技术设计

## ① 什么时候进入这个模式？

**触发意图**（满足任一即进入）：

1. 需求分析完成，用户说“继续设计”“出方案”“怎么实现”。
2. 用户一开始就要求“帮我设计某系统”，且需求边界已经足够清楚。
3. Review 发现实现方案方向有问题，需要回到技术设计。
4. Task breakdown 前发现缺少共享架构、模块边界或技术取舍。
5. 用户要求比较方案、评估技术路线、明确风险与边界。

**AI 自判原则**：

技术设计不是写代码前的形式文档，而是决定“用什么路径解决问题”。如果需求仍不清楚，先退回需求分析；如果只是局部实现细节，不要把它伪装成架构决策。

**降智期提醒**：

不要把“标准 CRUD”“沿用现有模式”当成设计。任何会影响模块边界、数据结构、依赖、接口、成本或长期维护的事项，都要在这里写清楚。

## ② 进入后大概怎么做？

**必须覆盖的核心要点**：

1. 读取需求 spec，确认没有未处理的必问项。
2. 自己先草拟方案：目标、约束、模块、数据流、风险、替代方案。
3. 使用推荐 sc 指令增强架构、调研和现有代码影响分析。
4. 把完整 proposal 发给 Codex，让 Codex 独立提出方案和质疑。
5. 收到 Codex 回复后写 4 段反思，每段有具体推理。
6. 多轮协商直到共识，或在一轮无新增信息时升级用户。
7. 扫描必问 12 类：依赖、API/schema、migration、成本、合规、业务规则等。
8. 把用户需要拍板的事项用业务语言呈现，不用纯技术术语轰炸。
9. 闭环问答规则：命中用户拍板项时，必须攒齐同批全部命中项，在当前终端一次性提问并阻塞等待用户答复；等待期不落正式档（不调用落档 lib）；Console 派发的 anchor 会话同样挂着等（anchor 是交互式 Claude TUI，非后台进程）。拿到答案后写入闭环记录（答案 + 理由）才落正式档。
10. 技术设计拍板项包括 migration 方向、依赖、schema、API 取舍、成本、许可证等用户权利项。
11. 写技术设计文档：必须按 `su-ccb-claude-plugin/templates/docs/03_开发计划/_模板_技术设计.md` 的核心章节组织，至少覆盖「一、设计概述」「二、方案与架构」「四、核心流程 / 逻辑」「五、测试策略」；涉及数据、接口、文件结构、迁移风险时补对应章节。同时遵守 `references/kernel/document-expression-spec.md`：「一、设计概述」首块为目标对齐白话叙事段（表格前），「四、核心流程」含端到端走查示例（或显式豁免），frontmatter 写 `expression_spec: v1`。
12. 判断是否自动进入任务拆分。

**深度说明**：

第 2 点要求你先有自己的方案。直接问 Codex“你觉得怎么做”会让协商变成外包判断，而不是两个 AI 的深度讨论。你必须先暴露自己的假设，Codex 才能质疑。

第 4 点的 proposal 不能太短。至少包含：你推荐的方案、你拒绝的方案、你担心的风险、你希望 Codex 挑战的地方。浅 proposal 只能得到浅回复。

第 7 点不要把技术选择包装成纯工程自治。引入依赖、改 schema、产生付费成本、影响公共 API，都属于用户权利或长期项目方向，必须问用户。

## ③ 什么时候算这个模式完成？

**必须同时满足**：

1. 技术设计文档已写好，包含架构、模块边界、数据流、选型理由和风险。
2. 所有命中的必问项已处理：已获用户答复、引用已有用户决定，或说明不命中理由。
3. Claude 与 Codex 已达成共识；若没有共识，已把分歧升级用户。
4. 至少 1 段 4 锚点反思已写入 spec 或 EventJournal。
5. 不存在“设计待定但继续拆任务”的情况；命中用户拍板项未闭环时不得完成技术设计或进入 task_breakdown。
6. 已明确哪些是 AI 自决实现细节，哪些是用户授权事项。
7. 已判断是否进入 task_breakdown。

**关于“命中”的定义**：

技术设计里最常命中的必问项是依赖、schema、公共 API、migration、成本和许可证。没有命中时要说明理由；命中时不能靠“我认为合理”跳过用户。

**完成后去向**：

如果用户目标包含交付实施，自动进入 task_breakdown。若用户只要求方案评审，则输出技术设计摘要并自然停下。

## ④ 不能干什么？（硬约束）

**绝对禁止**：

1. 跳过 Codex 协商直接定方案。
2. 未问用户就引入或移除依赖。
3. 未问用户就改公共 API 或 schema。
4. 未问用户就决定数据库 migration 方向；可以设计候选方案，但不能替用户拍板或执行。
5. 用“标准 CRUD”“沿用现有”替代真实设计。
6. 只写实现步骤，不写架构取舍。
7. 把许可证、成本、隐私或合规问题藏在技术细节里。

**为什么这些是硬约束**：

技术设计决定后续拆分和实现方向。这里的错误通常不是单个 bug，而是整条执行链跑偏。强制 sc、强制协商和用户必问，是为了让方案在开工前被充分挑战。

## ⑤ 推荐的 sc 指令（本节点强烈推荐使用）

**第一阶段 —— 草拟方案前**

- `/sc:design <系统或模块名>`
  - 用途：生成系统架构草图、关键组件和数据流。
  - 为什么强烈推荐：避免从代码细节开始想，先形成架构全貌。

**第二阶段 —— 草拟方案后、找 Codex 前**

- `/sc:research <核心技术领域>`
  - 用途：调研 ORM、缓存、队列、并发、协议或第三方方案。
  - 为什么强烈推荐：选型容易凭直觉，调研能暴露盲点。

- `/sc:analyze <现有代码路径>`
  - 用途：评估对现有代码、模块边界和测试面的影响。
  - 为什么强烈推荐：方案不能孤立成立，还要能落地。

**第三阶段 —— 升级用户前**

- `/sc:business-panel`
  - 用途：从成本、风险、维护、合规和用户价值复核方案。
  - 为什么强烈推荐：技术上正确不等于业务上合理。

**工程兜底**：

sc 不可用时继续工作，但必须说明跳过哪个 sc、原本解决什么问题、如何用自己分析或 Codex 协商补位。

## ⑥ 好 / 中等 / 坏输出样例

**好的样子**：

```markdown
方案目标：在不依赖 Console 写业务字段的前提下，让 plugin 直接产出 breakdown draft 文件。

我的初始方案：
- 真相源：`docs/.ccb/drafts/breakdown/<requirementId>.json`
- 写入者：plugin runtime
- Console：watch 文件后投影展示
- 风险：并发写、schema drift、用户审查状态

跑了 `/sc:design`，补充出 draft lifecycle。
跑了 `/sc:analyze apps/ccb-console/server`，确认现有 Console API 不在本 SP 范围内删除。

Codex 协商：
- 第 1 轮：Codex 反对我直接复用旧 Console POST 语义，指出这违背 plugin 独立。
- 第 2 轮：我们达成“文件真相 + Console 投影”的设计。

用户必问：
- 是否接受新增 draft 文件路径约定？命中 schema/API 语义变更，需用户拍板。

最终设计：
- draft 文件路径、字段、审查门、失败恢复都写入技术设计。
```

**中等但不合格的样子**：

```markdown
技术方案：沿用现有 API，把数据写入 breakdown draft。
Codex 说可以。
风险：注意并发。
```

不合格原因：没有解释为何沿用 API，没处理 plugin 独立，没 sc 增强，没用户必问，协商无实质。

**差的样子**：

```markdown
方案就是标准前后端 CRUD，后续实现再细化。
```

差的原因：空泛、不可执行、没有取舍、没有风险、没有协商。

**审计提示**：

检查技术设计时，至少看五点：有没有候选方案、有没有拒绝理由、有没有 sc 记录、有没有 Codex 质疑、有没有用户授权记录。缺任一项都可能是假设计。

**节点自检清单**：

1. 我是否确认需求 spec 没有遗留 TBD 或未闭环用户拍板项？
2. 我是否先写了自己的方案，而不是把判断外包给 Codex？
3. 我是否列出至少一个被拒绝方案？
4. 我是否说明了推荐方案的业务理由？
5. 我是否说明了推荐方案的工程代价？
6. 我是否运行或替代覆盖了 `/sc:design`？
7. 我是否运行或替代覆盖了 `/sc:research`？
8. 我是否运行或替代覆盖了 `/sc:analyze`？
9. 我是否在用户拍板前做了业务视角复核？
10. 我给 Codex 的 proposal 是否完整？
11. Codex 是否提出不同方案或明确风险？
12. 我是否写了 4 锚点反思？
13. 我是否把依赖变更列为必问？
14. 我是否把 schema/API 变更列为必问？
15. 我是否把 migration 方向列为用户拍板，而不是执行动作？
16. 我是否把许可证、成本、合规作为用户权利问题处理？
17. 我是否区分了“AI 自决实现细节”和“用户授权事项”？
18. 我是否写清集成边界？
19. 我是否写清不做项？
20. 我是否写清测试策略？
21. 我是否避免删除或修改 Console 业务代码？
22. 我是否记录了 EventJournal？
23. 我是否判断了是否进入 task_breakdown？
24. 若仍有分歧，我是否升级用户而不是强行定案？
25. 用户只读本设计时，是否能理解方案取舍？

**常见打回原因**：

1. 只有推荐方案，没有替代方案。
2. 只有技术理由，没有业务理由。
3. 只有模块名，没有数据流。
4. 只有实现步骤，没有架构边界。
5. 只有 Codex “同意”，没有真实反驳。
6. 没有处理依赖、schema、API、migration 的授权。
7. 没有说明不做项。
8. 没有测试策略。
9. sc 不可用但没有替代说明。
10. 用户读完仍不知道为什么选这条路线。
